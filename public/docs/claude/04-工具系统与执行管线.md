# 工具系统与执行管线 —— 策略与能力的解耦

> 本文是 Claude 基于源码阅读的独立解读，非官方文档。对应源码：
> `packages/core/tools/src/index.ts`（ToolRuntime）、`packages/core/agent-loop/src/tool-calls.ts`（调度器）、`packages/core/tools/src/ptc.ts`（PTC 程序化工具调用，0.1.2 前叫 code-mode.ts）。

## 设计目标

dsh 把"工具"拆成了四个正交关切，各归其位：

1. **能力本体**（tool 的 `execute()`）—— 只管做事，返回一个规范 JSON 值
2. **策略**（允许/拒绝/询问/超时/重试）—— 挂在管线事件上，工具本体零感知
3. **模型呈现**（`output.render`）—— 规范值 → 模型可见文本
4. **UI 呈现**（`presentCall`/`presentResult`）—— 纯函数渲染卡片，回放安全

这样做的直接收益：沙箱插件、权限插件、hook 桥（Claude Code/Codex hooks）、计费/审计插件可以**横跨所有工具族**生效，而任何一个工具都不需要 import 任何策略服务。

## 注册：一切皆效果（effect）

```ts
// packages/core/tools/src/index.ts:1037
register(definition: ToolDefinition): () => void
restrict(filter: ToolRestriction): () => void   // :1071 按 scope 过滤全局工具集
guard(guard: ToolGuard): () => void             // :1110 单调最终否决
schemas(scope?: ScopeKey): ToolSchema[]          // :1234 模型可见投影
```

- `register()` 返回 disposer——插件卸载即注销，热重载天然成立。
- `restrict()` 是**按交集组合**的作用域过滤器：被滤掉的全局工具在 prompt 里不出现、执行时也拒绝，与"不存在"不可区分。这就是"渐进式工具披露"（ToolSearch 类功能）的实现原语。
- `guard()` 注册**单调守卫**：只能否决或弃权，后来的监听者不能推翻——用于"必须不可绕过"的不变量（如 plan mode 禁写）。
- 作用域遮蔽（shadowing）：同名的 scoped 工具替换全局同名工具，仅对该 agent 生效——这是"每 agent 工具变体"和 persona 的机制。

## 执行管线全景

模型发出 tool-call 后，一次调用要过完整的关卡链（对照 `docs/tool-execution-pipeline.md` 与源码 `execute()` :1342）：

```text
tool/call 落日志（先记录，后执行）
  → tools/pre-execute (waterfall)     可扩展策略层：allow / deny / ask
      ask → ctx.approval 一次性审批    无应答者 = fail-closed 拒绝
  → 单调守卫 guards                    deny 或弃权；身份受保护
  → tools/execute (waterfall)          环绕派发：超时/重试/指标；只有 exec.signal 可替换
      → 工具本体 execute(args, exec)
          → fs/write-intent 等子门     （仅 tool-fs 变更类）
          → 工具自有事件落日志          todo/write、fs/observed、hook/invoked…
  → tools/post-execute (waterfall)     接受 / 拦截 / 替换结果 / 附加上下文
  → 注册表外层规范化                    任何 throw → isError 结果，绝不炸管线
  → ToolDefinition.finalizeContent     最后的内容级不变量（调用开始时快照）
  → tools/result (同步通知)            冻结的权威结果，只读观察
  → tool/result 落日志                 唯一模型可见结果 + meta（UI 卡片回放数据）
  → additionalContexts FIFO            附加上下文以 user/message 注入下一步
```

值得学习的三个硬核细节（都在 `createExecution()` :1364 附近）：

1. **参数身份保护**：`arguments` 被无损 JSON 快照后 `deepFreeze`，连同 `callId`/`name`/`token`/`signal` 全程不可变。只有 `tools/execute` 包装器拿到可变视图，且只允许替换 `exec.signal`（实现超时），不允许移除。
2. **finalizeContent 先于参数物化捕获**：参数的 getter 可能在 `snapshotJsonValue` 期间搞事（替换/清空回调），所以回调在最开始就 bind 快照——防御"恶意 getter"级别的严谨。
3. **失败即 isError，永不炸循环**：schema 校验失败、渲染器失败、无损 JSON 失败、body throw——注册表全部收容成 `isError` 结果。基础设施失败才 throw；领域上的"非理想结果"（如进程非零退出）应表达在规范值里。

## 调度：barrier 与滚动池

`executeToolCalls()`（`agent-loop/src/tool-calls.ts:59`）按**执行模式**给一个 step 里的多个 tool-call 分组：

- `exclusive` 调用形成 **barrier**（独占屏障）
- `parallel` 调用进入**有界滚动池**，启动前会**重新分类**（注册表变化影响未启动的调用）
- 派发可以重叠，但**策略、结果落日志、附加上下文严格按模型顺序提交**
- 中止时：已启动的调用排空并提交，未启动的记录合成错误结果——**回放永远合法**

`concludeTurn()` 是单调的"终结 turn"标记：成功的终结型工具（如 plan 退出）调用它，同 step 后续调用仍可被守卫，step 结束后循环停下。

## defineTool：类型安全的糖

`defineTool` 在 `ToolDefinition`（raw JSON-Schema，MCP 工具走这条路）之上提供：

- 参数 DSL → 编译期 `InferArgs` 推导 + 运行时校验（类型/必填/字面量/恰一联合/嵌套）
- `output.schema`（规范值 schema）→ 运行时校验 + `output.render(args, value)` 分离"程序值"与"模型话术"
- `presentationMeta(args, value)` → 持久化到 `tool/result.meta`，回放时喂给 `presentResult`
- 展示路径**软校验**：旧日志里的畸形参数让包装器返回 `undefined`（回退通用卡片）而不是 throw——**展示绝不能弄崩回放**

## UI 卡片：五种渲染意图

`presentCall`/`presentResult` 返回 `card` 标签联合：`generic` / `terminal` / `diff` / `search` / `web`。铁律：

- **纯函数**——live 流式和日志回放共用同一条渲染路径，禁止 I/O、禁止读会话状态、禁止时钟/随机。
- **UI 格式不进模型结果**——``` ```console ``` 围栏、diff、相对路径美化都不属于规范值。
- 工具永不 import UI 或传输类型；宿主/客户端各自把 `card` 映射成自己的视图。

## PTC（程序化工具调用）：把工具集变成编程 API

> 📌 **0.1.2 起改名**：本节机制原名 **Code Mode**，0.1.2-alpha 正式更名为 **PTC = programmatic tool calls（程序化工具调用）**，用户可见文案为「PTC mode / PTC 模式」。下文用新名，改名细节见本篇末尾的 0.1.2 增量。

`ptc.ts`（原 `code-mode.ts`）实现了一个漂亮的能力：模型不逐个调工具，而是写一段程序通过保留工具 `run_code` 执行，程序里 `await tools.<name>(args)` 直呼任何可见工具。

- 类型来自同一套 schema 自动生成（`ToolArgsMap`/`ToolOutputMap`，另有 ts-types.ts / py-types.ts 生成 TS/Python 声明）
- 子调用**重入完整管线**：携带 parent token、落 `tool/code-dispatch` 日志、拒绝以绑定异常形式返回
- 成功解析为**策略之后的最终规范 JSON 值**（不是渲染文本）——这就是为什么 `output.schema` 必须设计成"诚实的程序 API"
- PTC 塌缩（collapse）时直呼工具被**确定性拒绝**，拒绝信息明确指路"请在 run_code 里调用"——避免模型误判部署坏了；且这种塌缩调用在策略管线**之前**终止，审批者永远不会看到（更不会批准）一个只能失败的调用

## 长时任务：jobs 接缝

`run_in_background` 模式下，工具通过 `ctx.jobs.start({ kind, label, owner, run })` 发布后台工作，返回 `{ kind: 'background', jobId }` 规范句柄。关键生命周期规则：**id 一旦发布，外层调用取消不再杀死已发布的工作**——`job_kill`、owner 销毁、服务 teardown 才拥有那条命。前台工作则始终跟随 `exec.signal`。

## 📌 0.1.2 增量（rc.8 → 0.1.2-alpha.2，commit 141eb6f → 0a53fb5）

### 一、Code Mode → PTC：一次"零别名"的彻底改名

同一功能长期有两套名字：传输/注册表侧写 `code`/`code-mode`，而客户端预设早已以「PTC mode」发布。0.1.2 一次性统一为 **PTC = programmatic tool calls**（[官方 Note](../deepseek-harness/.agents/notes/implemented/architecture/2026-08-25-rename-code-mode-to-ptc.zh.md)），**不留任何兼容别名**：

| 项 | rc.8 | 0.1.2 |
|---|---|---|
| 配置值 | `tools.mode: 'code'` | **`'ptc'`**（`ToolPresentationMode = 'native' \| 'ptc' \| 'both'`） |
| 源文件 | `src/code-mode.ts` | `src/ptc.ts` |
| 分发 waterfall | `tools/code-dispatch-log` | `tools/ptc-dispatch-log` |
| 提示词分节 | `tools:code-only` | `tools:ptc-only` |
| 出厂预设 | `presets/code/`（id `code`） | `presets/ptc/`（id `ptc`） |

**故意不改的三类**，理由都很讲究：
- `run_code` 工具名及其 `code` 参数——它们命名的是**程序载荷，不是模式**，而且是模型可见的 API 表面；
- `dsh-code-runtime*` 包族、`ctx.codeRuntime`、`CodeSdkLanguage`；
- **持久会话词汇**：`tool/code-dispatch`、`tool/code-dispatch-start`、日志插件名 `tools-code-mode`、子调用 id 段 `:code:`——改它们会让改名前的会话日志读不出来，所以被**压在 `SESSION_FORMAT_VERSION` v0→v1 迁移那个 PR 里**。

于是留下一个**故意的命名不对称**，值得记住：标识符/配置/事件说 `ptc`，持久日志说 `code`。旧配置 `mode: code` 在本构建**直接不支持**（无别名，fail loud）。

### 二、工具 UI 卡片改由客户端派生——插件作者必读

rc.8 的做法：宿主在**读路径**上跑呈现器（查工具注册表、恢复呈现器作用域、回扫 `callId` 找调用名与参数、调 `presentCall`/`presentResult`），把渲染意图作为 `SessionEventEntry.view` 送下线。0.1.2 把这条路彻底拆掉（[官方 Note](../deepseek-harness/.agents/notes/implemented/architecture/2026-08-23-client-derived-tool-presentation.zh.md)）：

- **会话日志线上只传原始事件**：wire 条目就是 `{ type: 'event', event }`，`SessionEventEntry.view`、`SessionToolView`、`callView`、`resultView` 全部删除。
- **客户端自己派生**：`ui-tool` 的 card model 从原始 `tool/call` 参数 + `tool/result` 内容/错误 + 持久化的 `meta` 推导 props，按**线上工具名**经唯一 keyed slot `tool.call.toolview` 派发。

⚠️ **对插件作者的实际影响**：宿主侧 `presentCall`/`presentResult` **仍然存在、仍是纯函数、仍有测试**，但**内建 Web 客户端不再消费它们**——也就是说，**给新工具定义 presentCall/presentResult 不再能得到一张 Web 卡片**，你必须在客户端插件里注册 `tool.call.toolview` 的 keyed renderer。这是"接口保留、消费者搬家"的典型陷阱，官方 cookbook 已更新，但 `docs/subsystems/tools.md` 尚未（见下方漂移）。

能这样拆的桥梁是 rc.8 就有的 `presentationMeta` → 持久化 `tool/result.data.meta`（逐字节保留）：读取行结构、已应用的 diff 块、搜索分组与截断、web 来源这些**无法从模型可见文本无损恢复**的事实，本来就存在日志里。

三条新规矩：结构化卡片（terminal/diff/read/search/web）只接受**无 `parentCallId`** 的块（PTC 子调用一律走 Generic）；缺调用头就是 Generic（**不回扫、不额外 RPC、不猜**）；缓存必须以**不可变块身份**为键（实现是 `WeakMap<ToolCallBlock, …>`，不是 callId）。

### 四、其他

- **六段管线零结构变化**：`tools/pre-execute` → 单调守卫 → `tools/execute` → 工具体 → `tools/post-execute` → finalizeContent/规范化 → `tools/result` 一字未动，只有上面那个事件改名。`tools/ptc-dispatch-log` 不是第七段，它是 `run_code` 传输在每个**已结算子分发**上跑的旁路 waterfall，**只能改写持久日志副本**（程序已经拿到结构化值，模型两者都看不到）——所以 spill 策略在这条臂上敢 spill `read` 子调用（日志副本不是模型上下文，不会产生 read→spill→read 循环）。

- 新增模型可见工具 `list_subagent_models`（模型可选的子代理路由）；`CallId` 类型改名 `ToolCallId`。

## 📌 rc.8 增量（rc.5 → rc.8）

**Python Code Mode 起步（fd3 协议层）**：新包 `code-runtime-python` 落的是**纯线上契约**——`python3 -I` 子进程经 fd 3 跑 JSON-lines 帧协议（`boot → run → call/reply* → done`），本包只有协议词汇 + Python TypedDict 镜像，不含执行后端（官方把 9000 行 PR 按层拆栈发布，包骨架先行是因为 workspace 门禁无条件读每个 package.json）。看点有二：① 协议**无版本字段**——漂移由编译期 roster 断言 + 真 `python3` 镜像 e2e 抓，② `validateChildFrame()` 把子进程当敌手：伪造的 `truncated` 非字面 `true` 不算、`1e400` id（JSON.parse 后 Infinity）直接拒——"进程边界必须运行时验证"纪律的教科书实现。跨语言可移植性靠**构造保证**：保留字集合 = ECMAScript ∪ Python 关键字，两个后端强制同一套。`ctx.tools` 的 code-mode 消费端在 rc.5 就按 `CodeRuntime.language` 分派（typescript/python 双 flavor），未知语言 fail-loud。

**web_search 改多查询**：模型 schema 从 `query: string` 变 **`queries: string[]`（必填）**——动机是行为观察：模型偏爱能一次带多个关键词的 MCP 搜索工具，甚至原生搜完再补一次 MCP。上限默认 4（对齐 Codex web.run），先验数量再去重；多查询并发扇出、按 rank 轮转合并去重、**任一失败整体失败**。接缝没动——`WebSearchProvider.search` 仍是单查询契约，扇出住在工具消费者里（版本教训：这是模型可见 schema 破坏，会掉一次前缀缓存）。

**持久 PowerShell（tool-pwsh-persistent）**：`ctx.terminals` 注册表与 `terminal-bash` 后端**共享**，后端加 `shellDialect: 'bash' | 'pwsh'` 开关——两方言发同一个 OSC `133;D;` 提示符标记，`sanitize.ts` 的就绪检测零改动复用；Windows 侧 `subprocess-local` 新增 koffi 探测器（Toolhelp32 + 创建时间身份防 pid 复用）。配套修复：`tool-bash-persistent` 曾用自定义 `PS1` 覆盖后端受控提示符，把快速就绪通道打死（每次调用白等 3.5s）；修复= 后端在 `PROMPT_COMMAND` 里**自修复 PS1** + 工具信任接缝信号，实测 3540ms → **86ms**。

**Code Mode 小改**：带图像的子工具结果现在经 `exec.deferContext()` 延后为 run 之后的 user 消息（图像不再卡在嵌套调用里）。

| 你想做什么 | 用哪个扩展点 |
|---|---|
| 可扩展的允许/拒绝/询问策略 | `tools/pre-execute` waterfall |

| 超时/重试/指标（包住派发生命周期） | `tools/execute` waterfall |

| 按会话裁剪工具集 | `ctx.tools.restrict()`（scoped） |
| 每 agent 的同名工具变体 | scoped `register()` 遮蔽 |
