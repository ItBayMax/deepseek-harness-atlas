# 14 · 远程执行接缝与账号体系

> 基线：`dsh@0.2.0-rc.2`（commit `639ed01539`）。
> 0.1.2 时远程执行由第三方云沙箱 E2B 提供（`e2b` / `fs-e2b` / `subprocess-e2b` 三个包），没有账号体系。
> 0.2.0 把 E2B **整组删除**，换成自建的 SSH provider family；同时引入了完整的第一方账号体系。

## 一、为什么用 SSH 换掉 E2B

这是一次**两篇 Note 配对**的架构迁移，退役侧和新建侧同日提交，互相交叉引用：

- `simplification/2026-09-11-remove-e2b-providers`
- `architecture/2026-09-11-posix-ssh-runtime`

### 真正的触发点不是"贵/慢/不稳"

而是一个具体的技术死结：**PTC 需要一条与程序 stdin/stdout/stderr 相互独立的双向控制流**
（见 [04 工具系统](04-工具系统与执行管线.md)的 PTC 章节），而被 pin 住的 E2B SDK：

- 只暴露标准进程流和 PTY 输出，**没有额外的描述符传输**。在 VM 内部创建一个 fd
  并不会把它暴露给 Harness 宿主。
- 更致命的是：**即使消费者施加背压，该 SDK 也会完整保留 stdout/stderr**——
  所以"流级队列上限"根本无法约束宿主内存。

结论写得很直白：继续扩展这个 adapter 会把"一个实验"变成"**一个独立的远程传输项目**"。

### 被否决的方案（这才是 Note 最值钱的部分）

| 方案 | 否决理由 |
|---|---|
| 在 E2B 标准流上多路复用控制通道 | 中继可以打帧，但还要按通道的流控与关闭语义、有界队列，以及解决 SDK 累积输出保留——"**这些是远程传输语义，不是描述符管道**" |
| 只用 SFTP 替代远程文件操作 | SFTP 提供传输，但**不能保留现有的受保护原子写、edit、policy 和错误语义**。复用远端的 local 文件 provider 让这些机制留在原 owner 手里 |
| 为程序流暴露 TCP/HTTP 端点 | 引入远程端口暴露、端点认证、服务器部署。转发 Unix socket 复用已认证的 SSH 会话 |
| 把整个 Harness 搬到远程主机 | 那是另一种部署模型——它把模型凭据、会话存储和插件状态**跟着执行一起搬走**，而不是为现有能力提供远程实现 |

## 二、`ctx.ssh`：星形结构，不是链式

```ts
// packages/ssh/ssh/src/index.ts:42-44
declare module '@deepseek-ai/cordis' {
  interface Context { ssh: SshConnection }
}

/** One non-reconnecting SSH session; loss invalidates all active operations. */
export class SshConnection extends Service {
```

四个包是 **1 个 Service + 3 个互不依赖的 Provider**：

| 包 | 职责 | 提供的接缝 |
|---|---|---|
| `ssh` | 连接、helper 身份、传输生命周期 | **定义** `ctx.ssh` |
| `fs-ssh` | 远程文件身份、读取、受保护的原子变更 | 提供 `ctx.fs` |
| `subprocess-ssh` | 可执行文件查找、进程、控制流、终端 | 提供 `ctx.subprocess` |
| `sandbox-ssh` | 远程 file-effect 限制与强制事实 | 提供 `ctx.sandbox` |

三个 provider 全部 `static inject = ['ssh']`，**互不依赖**，只通过两个原语工作：

- `ctx.ssh.request(method, params, schema, signal, wait)` —— 管理 RPC（JSON，走 SSH exec 流）
- `ctx.ssh.connectStream(endpoint, signal)` —— 转发一条已认证的独立 SSH channel

`sandbox-ssh` 全包只有 33 行，是分层最清晰的体现：

```ts
// packages/ssh/sandbox-ssh/src/index.ts:9-17
/** Resolve each confinement request on the same host as its filesystem and subprocess providers. */
export class SshSandboxProvider extends SandboxProvider {
  static inject = ['ssh']

  override async confine(argv: readonly string[], policy: SandboxPolicy, signal?: AbortSignal): Promise<ConfinedArgv> {
    signal?.throwIfAborted()
    try {
      const confined = await this.ctx.ssh.request('sandbox', { argv, policy }, factsSchema, signal)
```

它**自己不做任何策略决定**——把 `{argv, policy}` 原样发给远端 helper，
helper 在**文件所在的那台机器上**问它自己加载的 local sandbox provider 要强制执行用的 argv。

> 顺带澄清一个常见的层级错位：`shell/bash-sandbox` **不是** `ctx.sandbox` 的 provider，
> 它是 `ctx.shell` 的一个 **executor（消费者）**，调用 `ctx.sandbox.confine(...)`。
> 正确的同层对照是 `sandbox-local` ↔ `sandbox-ssh`——两者是平行 provider，
> 消费者 `bash-sandbox` 对两者都适用、无需改动。

## 三、为什么强调 POSIX

Note 里有一条关键的设计原则：

> *"Provider paths describe the execution world without a separate local/remote flag."*
> *"Path canonicalization belongs where the files exist."*

即：**不引入 `isRemote` 这类元数据标志**。执行世界靠 provider 本身描述，
路径规范化由**文件真正所在的那个文件系统**来做。

要让这个"无标志"设计成立，两端的路径语义必须一致。所以 POSIX **不是"顺便只支持 Linux"，
而是这个设计的前提条件**：

```ts
// packages/ssh/ssh/src/index.ts:73-80
  constructor(ctx: Context, config: Config) {
    super(ctx, 'ssh')
    if (process.platform !== 'linux' && process.platform !== 'darwin') throw new Error('SSH runtime requires a POSIX client')
    this.config = z.object({
      host: z.string().regex(/^[a-zA-Z0-9][a-zA-Z0-9_.@-]*$/),
      node: z.string().startsWith('/'), helper: z.string().startsWith('/'), ...
```

**本地客户端也必须是 POSIX**，不只是远端。Windows 宿主用不了。

## 四、安全设计要点

- 私有管理 RPC 走 helper 的 SSH exec 流；**每条程序流走各自独立的 SSH channel**（转发 Unix socket）
- **每条流拿到一把全新的 256-bit TLS 预共享密钥**，通过私有管理 RPC 下发，TLS 1.2 双向认证，
  **密钥绝不作为流前缀传输**。理由写得很清楚：**仅靠 socket 权限不够**——
  file-effect 限制可能允许同用户连接，或在可写临时目录里替换路径名
- 就绪检查校验已安装 helper 的摘要。Note 诚实地限定了边界：
  **这些检查钉住的是预期部署产物，不能认证一个恶意的远程操作系统**
- **连接丢失不重连、不重放**：租约到期不能被客户端当成"已成功终止"；
  被中断的变更或启动的结果是未知的，**必须如实上报**

## 五、⚠️ SSH 尚未在任何出厂 profile 中挂载

全仓 `package.json` 检索确认：`dsh-ssh` 系列包**只被 `packages/ssh/` 内部四个包互相引用，
没有任何 app / profile / bundle 依赖它们**。

Note 也明确限定了初始组合范围是 **POSIX headless 和自定义 profile**，
并说"带宿主文件系统假设的 Web workspace 消费者需要自己做集成——
**仅替换 provider 并不能让那些视图变成远程感知的**"。

> 所以任何"升级到 0.2.0 即获得 SSH 远程执行"的说法都是不准确的。
> 正确表述：**SSH provider family 已实现并可用于自定义组合，但未在任何 shipped profile 中默认挂载。**

## 六、账号体系：两条并行路由，互不回退

### 包分工

```
credentials/deepseek-account            Service Definition（抽象类），定义 ctx.deepseekAccount
credentials/deepseek-account-platform   唯一实现：PKCE/OAuth、GrantRecord 持久化、登出重试
llm/llm-deepseek-account                注册 provider 路由 "deepseek-account"，认证头 x-dsh-auth-token
llm/llm-deepseek-api-key                注册 provider 路由 "deepseek-official"，认证头 x-api-key
llm/llm-deepseek                        从「插件」降级为「共享协议库」
api/account-controller                  Remote RPC 暴露面
client/ui-settings-account              Desktop-only 账号 UI
```

### 两条路由的关系

Note 原话：

> *"`deepseek-official` and `deepseek-account` are **independent routes sharing the DeepSeek
> protocol implementation**. Each adapter has exactly one credential resolver and authentication
> header mode. **Neither route falls back to the other credential.**"*

| | `llm-deepseek-api-key` | `llm-deepseek-account` |
|---|---|---|
| 路由名 | `deepseek-official` | `deepseek-account` |
| 认证头 | `x-api-key: <key>` | `x-dsh-auth-token: <token>`（**无 Bearer 前缀**） |
| 凭据来源 | `.credentials.yaml` 的 **`refs:`**（裸 key） | `.credentials.yaml` 的 **`records:`** 中的 GrantRecord |
| 配额错误码 | 通用 `QUOTA` | 改写为 `ACCOUNT_QUOTA`（触发充值入口） |

**重要后果**：模型选择器同时暴露两条路由，**即使已有 API key，选账号路由仍然必须登录**。

### `llm-deepseek` 的角色变化（容易踩的文档陷阱）

| | 0.1.2 | 0.2.0 |
|---|---|---|
| 形态 | **插件**：有 `name` / `inject` / `apply`，自己注册 `deepseek-official` | **协议库**：整个文件只剩 re-export（41 行） |
| 导出 | `apply()` / `resolveApiKey` / `registerConfigurableProviders` | `registerDeepSeekProvider` / `DeepSeekAdapter` / `DeepSeekFilesClient` |

所以凡是文档里写"在 `llm-deepseek` 里配置 API key"的，都应改为 **`llm-deepseek-api-key`**。

### 账号能力与明确的限制

`ctx.deepseekAccount` 提供 13 个方法（状态、资料、余额、赠送额度、登录/取消/登出、订阅、token 解析等）。
其中三条限制值得记住：

- **没有 token 刷新流**。README 的 Known Limitations 明写 *"Account tokens have no expiry or refresh flow."*
  失效是**被动**的：401 或业务码 `40003` 清掉本地 grant 并发 `deepseek-account/session-expired`。
- **登出的远程吊销最多重试 5 次**，重试任务不持久化、进程关闭即终止——
  所以**"已登出"不等于"远端 token 已失效"**。
- **账号 UI 是 Desktop-only**。Plain Web 保留 API-key onboarding，**没有账号订阅或登录**。

### 安全边界：凭据是 Host-only 的

`api/account-controller` 暴露 11 个方法，但**刻意不暴露** `resolveToken`、`getPlatformSession`、
`rejectToken`、`getDeviceIdentity`。README 原话：*"The API controller exports state and commands
**without resolveToken**."* —— **RPC 只过状态和命令，凭据不过线。**

## 七、✅ `.credentials.yaml` 格式未变（对运维文档的确认）

这是本轮少数被**证实仍然成立**的既有断言：

```ts
// packages/credentials/credentials-local/src/index.ts:169-175
export interface CredentialsDocument {
  refs: Map<string, string>
  records: Map<string, CredentialRecord>
}
```

```ts
// packages/credentials/credentials-local/src/index.ts:221-226
  for (const key of keys) {
    if (key !== 'version' && key !== 'refs' && key !== 'records') {
      throw new Error(`credentials-local: unknown top-level key "${key}" in ${filename}`)
    }
  }
```

`git diff` 显示整个区间内该文件 **−18 行、0 行新增，且删除的 18 行全部是重复代码检测注释**——
解析、写入、迁移逻辑一行未动。

两条补充给运维：

- **拒绝而非跳过**：未版本化的根、未知顶层 key、类型错误的值全部抛错。
  理由写在 JSDoc 里：*"a silently ignored entry reads as '**the credential I stored has no effect**'"*。
- ⚠️ **pre-release 迁移路径将被移除**：`renderFlatLayoutMigration` 的注释写着
  *"Remove with the pre-release stance at the first tagged release"*。
  如果环境里还有"裸 mapping 无 version"的旧扁平布局文件，**应在正式 tag 前完成一次启动迁移**。
  另外 **live reload 绝不迁移**，只有 boot 会。
