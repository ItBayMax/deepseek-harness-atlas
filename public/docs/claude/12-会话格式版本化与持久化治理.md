# 12 · 会话格式版本化与持久化治理

> 基线：`dsh@0.2.0-rc.2`（commit `639ed01539`）。本篇是 0.2.0 新增的领域——
> 0.1.2 时 `SESSION_FORMAT_VERSION` 还停在 `0`、"无兼容承诺"，一个版本周期后它变成了
> 一套**有版本、有迁移链、有机器校验的治理体系**。

这是本轮上游更新里**最值得抄的一套机制**。它回答的问题很多团队都遇到过：

> 我改了一个会持久化的类型，**这算不算破坏性变更？**

0.1.2 的答案是"不用管，pre-release 随便改，后端拒收旧格式就行"。
0.2.0 的答案是：**把这个判断从人肉 review 变成机器分类 + 人工举证**。

## 一、立场是怎么变的

`AGENTS.md` 开篇那一节被整节替换了——这就是"为什么现在是 0.2.0"的官方回答。

**旧（0.1.2）**：

> ## Pre-release stance: foundation over blast radius
> **Remove at the first tagged release.** …rename or repackage freely and update every reference.
> Backends reject old on-disk formats. `dsh-session` keeps `SESSION_FORMAT_VERSION` at `0` with no compatibility promise.

**新（0.2.0，`AGENTS.md:5-11`）**：

> ## Pre-stable APIs and released Session data
> …Adjacent migration may add a version-named successor but **never move, overwrite, or delete committed generations**…
> Record each externally perceptible breaking change **immediately** in an upgrade guide.

那句"第一个正式 tag 发布时删掉本节"**兑现了**。语义上 0.2.0 = 项目从
"随便改、磁盘格式随便拒" 跨到 "**已提交的会话数据世代不可动 + 破坏性变更必须当场写迁移指南**"。

## 二、版本常量：递增的判据挂在写入器上

```ts
// packages/core/session/src/types.ts:74-89
 * The version is a single monotonic integer with no major/minor split. Whether
 * a bump is needed is decided by what the WRITER emits, never by what a newer
 * reader can accept: bump exactly when an older runtime could no longer handle
 * a new log with full semantic correctness ("parses without error" is not
 * correctness — silently skipping content that shapes reconstruction is a
 * wrong read). Only structural changes reach that bar: the header shape, the
 * SessionEvent envelope, core event semantics, or the surface mechanism.
 * Adding an ordinary event type does not bump — the per-event
 * `ignorable` guard covers vocabulary growth instead. When in doubt, bump: a
 * near-identity upgrade step is almost free, a missed bump makes older
 * runtimes read new logs wrong silently.
export const SESSION_FORMAT_VERSION = 4
```

四条规则值得单独拎出来：

1. **单调整数，没有 major/minor**。版本号只回答"能不能读"，不表达"改动大小"。
2. **判据挂在写入器，不挂在读取器**——"新读取器能接受什么"不是依据。
3. **"能解析不报错" ≠ 正确**。静默跳过影响重建的内容就是错误读取。
4. **拿不准就递增**。理由是代价不对称：多一次近似恒等的升级步骤几乎免费，
   漏一次递增会让旧 runtime **静默地**读错新日志。

第 4 条是这套设计的价值观：**错误的事实比缺失的事实更有害，因为它看起来可信**。

## 三、迁移链：有状态流式 Stage

### 为什么不能用"整件式"迁移

第一版实现把整个日志当一件事迁移，结果一份 **116 MB** 的真实会话能把 **16 GB** 的 Node 进程吃爆。
Note 里的诊断非常具体（`2026-08-31-released-session-format-migrations`）：

- zstd 输入含 **317,540 个 frame**，每个 frame 单独异步解压 → 同等数量的 Promise 与线程池调度
- 已发布的打包 assistant chunk 会先展开成约 **914 万个** v0/v1 逻辑事件，
  再由 v1→v2 折叠成 **72,784 个** 当前事件——整件式 API 要求两种表示同时存活
- 每条迁移边前后都 deep freeze 一次完整快照

### 新设计

```
JSONL record
  → released physical row decoder
  → v0-to-v1 stage → v1-to-v2 stage → v2-to-v3 stage → v3-to-v4 stage
  → current event collector
```

链路里**没有 `flatMap`、没有中间事件数组、没有 scheduler**。核心是两个接口：

```ts
// packages/session/session-format/src/types.ts:124-139
/** A codec-owned compact run that adjacent migrations may consume without expanding. */
export interface SessionFormatEventRun {
  readonly runType: string
  readonly firstSeq: number
  readonly eventCount: number
  /** Expand the run for a migration that has no direct handler. */
  expand(): Iterable<SessionFormatEvent>
}

/** Synchronous output channel owned by a compiled migration stream. */
export interface SessionFormatMigrationContext {
  emitEvent(event: SessionFormatEvent): void
  emitRun(run: SessionFormatEventRun): void
}
```

**可抄的三个点**：

- **`expand()` 是惰性的**。打包 run 可以直接抵达需要折叠它的那条边，不必先物化 914 万个普通事件。
  这是把 116 MB 日志从 OOM 救回 **6.2 秒 / 2.1 GB 峰值**的关键。
- **生产者声明自己发的是单事件还是 run**，热路径不用靠属性推断类别。
- **Stage 是有状态的，每次恢复新建，绝不跨会话共享**。上游明确说：迁移本来就有状态
  （v0→v1 要跟踪 message 与 retry identity，v1→v2 要暂存未结算的 attempt），
  把状态藏在闭包里会让"运行结构"和"静态声明"分离。

### 逐跳改了什么

| 跳 | 性质 | 要点 |
|---|---|---|
| v0→v1 | 近似恒等 | 已发布 v0 的有限归一化：`steering/message`→`user/message`、`compact/*`→`compaction/*`、确定性补 id |
| **v1→v2** | **改变事件基数** | 顶层 `assistant/chunk` 被**折叠**进 `assistant/message.data.stream`；没有产生 surface message 的 attempt 变成 `assistant/attempt`；**物理层从此每行只存一个事件** |
| v2→v3 | 插入事件 | 系统提示词**提升为消息**（新增 `system/message`）；PTC 词表更名（见下） |
| v3→v4 | 表示重塑 | 工具结果提升为一等 `tool` 角色消息；父目录补全（新增 `subagent/catalog`）；新增 `developer/message` |

### Catalog：静态装配，不依赖已挂载的插件

```ts
// packages/session/session-format-catalog/src/generated.ts:15-31
export const sessionFormatCatalogOptions: SessionFormatCatalogOptions = {
  currentVersion: 4,
  codecs: [ releasedV0SessionFormatCodec, ..., releasedV4SessionFormatCodec ],
  currentEncoder: releasedV4SessionFormatCodec,
  migrations: [ sessionFormatV0ToV1, sessionFormatV1ToV2, sessionFormatV2ToV3, sessionFormatV3ToV4 ],
```

文件头注明是 `scripts/gen-session-format-catalog.ts` 生成的，并写了理由：
**直接 import 让历史可读性独立于已挂载的插件**。这是刻意拒绝了"让插件注册迁移"的方案——
否则"能不能读懂三个月前的日志"就取决于部署组合了。生成器还会反查链路能否到达
`SESSION_FORMAT_VERSION`，**少一条边直接生成失败**。

## 四、persistence-changes：把兼容性判断机器化

这是本篇的重点。位置 `docs/persistence-changes/`。

### 覆盖范围

生成器 `scripts/gen-persistence-catalog.ts` 提取四类"持久化根"：逻辑会话头、物理 JSONL 头行、
事件信封、以及每个仓库内声明的事件（当前 **59 个** `event:*` 根）。产物两份：
`docs/persistence-schema.json`（机器清单）+ `docs/persistence-catalog.md`（可读目录）。

**被引用类型的变更会传递**——改一个共享的 `Message` 声明，会同时点亮十个事件根。

### 四文件结构

每条带日期的记录有四个同目录文件：

| 文件 | 职责 |
|---|---|
| `YYYY-MM-DD-slug.md` | 英文确认文档，含 `kind: persistence-change` front-matter 与一段机器声明 |
| `.zh.md` | 中文对侧，**含完全相同的机器声明** |
| `.i18n.yaml` | 生成的双语一致性记录 |
| **`.schema.json`** | **生成的变更后完整 schema** |

`.schema.json` 是"变更后快照"，**下一条记录以它作为"变更前 schema"**，构成一条逐根的链表：

```yaml
# docs/persistence-changes/2026-09-16-session-format-v4.md
changes:
  - root: "SessionHeader"
    previous: "2026-09-11-initial"        # 前驱记录 id
    after: "1a3440e3577382704d42..."      # 变更后摘要哈希
    decision: version-bump
```

校验器拒绝：缺失前驱、环、同一根的重复后继、摘要不匹配、当前根与最新记录不一致。

**为什么这么设计**：比较**完全本地化**——"本地检查仅使用当前检出目录中的文件"，
不依赖 Git 引用、远端服务或已发布版本。不需要 checkout base 分支、不需要网络。

### 固定兼容性规则

| 检测到的变更 | 最低决策 |
|---|---|
| 添加可选事件体属性 | `same-version` |
| 必选属性改为可选 | `same-version` |
| 添加普通事件类型 | `same-version` |
| 为普通事件增加更高的 `data.version` 且**原样保留所有旧分支** | `same-version` |
| 可选改必选 / 添加必选属性 / 改已有类型 / 删除或重命名 | **`version-bump`** |
| **更改会话头或事件信封** | **`version-bump`** |

两条关键细节：

- **规则应用于整个变更**，所以允许的变更**不能掩盖**同时发生的破坏性变更。
- `--decision` 是**受检查的断言**，不是声明——写错会在落盘前失败。

### 两个巧妙的补充

**`@persistenceReserved`**：当读取器按属性名拒绝某个 JSON 字段时，把该属性声明为
**可选 `never`** 并打这个标记。提取器保留这个"禁止字段"，于是**以后允许该字段携带值时，
属于"已有字段类型变更"而非"新增字段"**——强制走 version-bump。
v4 用它登记了退役的 `request/header.system`。

**版本号本身被编码为字面量节点**：`SessionHeader.version` 在 schema 里是 `{"kind":"literal","value":4}`，
所以**头部版本递增本身就是一个结构变更**，会被机器检测到并要求 `version-bump`——**版本递增无法被遗漏**。

### 校验入口

| 命令 | 校验什么 |
|---|---|
| `pnpm run verify-persistence-changes` | 结构变更是否已记录、决策是否达标 |
| `pnpm run doc-sync` | 清单新鲜度、完整历史链、双语配对 |
| `pnpm run persistence-review --before X --after Y` | 只读 PR 评审路径，独立于确认历史 |

## 五、落盘规则与兼容边界

**文件名编码 generation**（`packages/session/session-format/src/filename.ts:14-18`）：

- v0 = `session.jsonl[.zstd]`
- 正 generation = `session.vN.jsonl[.zstd]`

**三条不可动摇的规则**：

1. **迁移绝不移动、覆盖或删除任何已提交 generation**，只写最终 current target。
   中间版本（v1/v2/v3）**只存在于 stage state，从不落盘**。
2. **只读打开不写盘**：`prepareJsonlMigration()` 只在内存里返回 current artifact。
   历史分页、导出、opening snapshot 都只需要这个——旧版要为此额外等约 2.2 秒**并修改存储**。
3. **`publish()` 一旦开始就运行到终态**，不接受取消；已发布的 generation 绝不回滚。

**兼容边界（诚实记录）**：

- ✅ 旧 v0 日志能读：catalog 注册了完整 v0→v4 链
- ⚠️ v0/v1 边**只接受冻结的第一方事件清单**，未知外部插件事件会让迁移失败
  ——**包括带 `ignorable: true` 的**（这是 alpha 策略，与运行时的宽容度不同）
- ❌ **无 downgrade、无自动 fallback**；v3 读取方拒绝更新的 generation

还有一条容易踩的规则，值得抄进任何做数据格式的项目：

> **产品的 alpha、beta 或 rc 发布都会确立已发布会话格式的义务。
> GitHub 的 prerelease 标记不会让持久化用户数据成为可丢弃数据。缺少发布记录不代表尚未发布。**

## 六、📌 对我们的直接影响

| 旧认知（0.1.2） | 0.2.0 事实 |
|---|---|
| `SESSION_FORMAT_VERSION = 0` | **= 4** |
| 落盘 `session.jsonl.zstd` | **`session.v4.jsonl.zstd`**（无 `.vN` 专指 generation 0） |
| 存储行是打包 chunk rows，字段 `seq0`/`time0` | **顶层打包行不存在了**；`seq0` 只活在冻结的 v0 解码器里 |
| 成员数组 `texts`/`args`、间隔数组 `dt` 在行上 | **字段名保留**，搬进 `assistant/message.data.stream[]` |
| 有 jsonl 和 sqlite 两种持久化 | **只有 JSONL 一种 first-party 实现**，sqlite 包已删且**无自动迁移** |
| `tool/code-dispatch*` 刻意保持不变 | **已改名 `tool/ptc-dispatch*`**（v2→v3），v4 硬拒旧名 |

最后一条对**任何直接解析 `session.jsonl` 的工具**都是硬伤——包括我们自己的
[dsh-replay-theater](https://github.com/ItBayMax/dsh-replay-theater)。节奏数据没丢，
但读法要从"扫顶层 `seq0` 行"改成"读 `event.data.stream[]`"。
