# 15 · 插件生命周期与可观测性

> 基线：`dsh@0.2.0-rc.2`（commit `639ed01539`）。
> **这一篇对我们最重要**——它直接关系到我们自己写的插件怎么装、怎么热更新、以及一条
> 被推翻的旧认知：**"任一插件失败 → 整棵插件树 abort"在 0.2.0 上已经不成立了。**

## 一、`boot/` 包组：把同一套装配搬进运行时

0.1.2 的三层组合（profile → bundle 层 → `cordis.patch.yml`）**完全保留**，
仍由 `app-boot` 在启动时装配。0.2.0 新增的是**第二条入口**：
同一份 patch 列表可以在进程存活期间被重新读取、重新组合，并打进正在跑的 Loader 树。

| 包 | 角色 | ctx key |
|---|---|---|
| `app-boot` | 从 `cordis.yml` 启动、套 profile/patch 层、报告启动失败 | （bins 的库） |
| `cmdline` | 应用自己拥有 flags / `--help` / exit code | `cmdlineArgs`, `appExit` |
| `hmr` | 协调模块重载、配置重载与包变更 | `hmr` |
| `config-editor` | 通过 Loader reconciliation 持久化活动 profile 配置 | `configEditor` |
| `plugin-manager` | 管理当前 profile 的插件与 bundle | `pluginManager` |

**关键事实：CLI `dsh plugin` 和 `ctx.pluginManager` 共用同一个实现模块**，不是两套代码。
Note 明说：*"Plugin Manager and `dsh plugin` call the same asynchronous package operations."*

启动器把 profile 事实以**纯数据**形式递给运行时（`ctx.profileContext`，
注释写明 *"contains no callbacks or mutation methods"*、*"Present only in a profile launched by dsh"*），
所以 base patch 里 `plugin-manager` 和 `hmr` 两行都用
`disabled: !!js "!ctx.get('profileContext')"` 做门控。

## 二、🔴 fail-loud 被推翻：只有 7 个必需条目能中止启动

这是本轮**对既有文档冲击最大的一条**。

```ts
// packages/boot/app-boot/src/index.ts:746-754
const requiredStartupEntryIds = new Set<string>([
  'agent-loop', 'webserver', 'modules', 'connection',
  'headless-runner', 'acp', 'sdk-jsonrpc-server',
])
```

```ts
// packages/boot/app-boot/src/index.ts:930-938
  const failures = await inactiveEntries(ctx)
  const required = new Set(failures.filter(({ entry }) => entry === bootstrapIncludes.get(ctx)
    || requiredStartupEntryIds.has(entry.options.id)).map(({ entry }) => entry))
  if (required.size > 0) {
    throw new StartupError(...)
  }
  if (failures.length > 0) warn(activationDiagnostic(binName, failures))
```

**第 938 行就是判决**：非必需条目的失败只 `warn()`，函数正常返回，**启动继续**。

决策记录：`architecture/2026-09-09-consumer-owned-startup-strictness`
> *"A listed entry that is present, enabled, and not active rejects startup…
> **Other inactive entries produce one warning and leave successful siblings running.**"*

### 同期还有第二处松动：Loader 明确非事务、不回滚

`simplification/2026-09-09-nontransactional-loader`（标题就叫"保持 Loader 变更非事务性"）：

> *"Loader changes entry options eagerly… **Neither restores a previous plugin or configuration.**
> Include retains parse validation and patch reapplication, but **plugin failures can leave a
> partially applied tree**."*
>
> *"A plugin activation failure can leave the new options and a failed fiber in place.
> Callers that require active plugins must audit after settlement."*

这个 PR **曾经**引入过事务性重载，后来被**整体 revert** 掉了。

### 给插件作者的直接结论

| 场景 | 0.1.x | 0.2.0 |
|---|---|---|
| 你的插件启动时崩了 | 整个 dsh 起不来 | **dsh 照常起来**，你的插件变成一条 stderr warning + 树里一个 failed fiber |
| 运行时热重载崩了 | — | 不拖垮别人，**但也不会自动回滚**；新 options 和 failed fiber 就留在那 |
| 源码模块 HMR 崩了 | — | **唯一带完整回滚的路径** |

诊断位置：0.2.0 起 CLI 会把完整诊断（原始 error 对象、import log）写到 `$DSH_HOME/logs/` 下的独立文件。

**运维含义**：0.2.0 上"服务活着"**不再等于**"插件都在"。判断仍然靠这一条：

```bash
journalctl -u dsh-web -n 300 --no-pager | grep -c 'failed to import loader entry'   # 必须是 0
```

## 三、"装插件要重启"也松动了

`ChangeResult.application` 有四个值：`applied` / `restart-required` / `overridden` / `failed`。
决定权在 **HMR 是否挂着**：

```ts
// packages/boot/plugin-manager/src/index.ts:776
  application: this.ownerContext.get('hmr') !== undefined ? 'applied' : 'restart-required'
```

| 操作 | 有 HMR | 无 HMR |
|---|---|---|
| 启/停已装插件 entry | **立刻生效** | restart-required |
| 选中/取消 bundle 层 | **立刻生效** | restart-required |
| **首次安装**一个新 bundle 包 | **立刻生效** | restart-required |
| **替换/升级一个已存在的依赖** | **restart-required** | restart-required |

最后一行有硬编码依据（`plugin-manager/src/index.ts:561`）：
`if (Object.hasOwn(before, name)) return 'restart-required'`。理由是
*"Configuration changes can reuse the loaded module cache, whereas **replacing installed
JavaScript needs a new process generation**."*

### 事务性的不对称

- **安装是事务性的**：pnpm 跑之前快照 `package.json` + `pnpm-lock.yaml`，
  失败/取消/装出来的包没有 `dsh.bundle` → 全部还原。
  **但 `pnpm-workspace.yaml` 故意不还原**——pnpm 11 的 `allowBuilds` 待决名单记在那里，
  要留给"允许脚本并重试"。
- **移除不是事务性的**：Note 明说 removals 保留部分状态 + 诊断路径。

### 保护名单

`protectedModules` 包含 loader / include / api-gateway / webserver / client-modules /
typert-registry / hmr / plugin-manager 自身等。含这些模块的 bundle 会被标 `managementBundles`，
**服务端拒绝自删自卸**。

## 四、HMR 的两条路径

### 路径 A：配置/组合重载（默认开）

监听 profile `package.json`、profile `cordis.patch.yml`、home `cordis.patch.yml` 三个精确文件
（默认 `awaitWriteFinish: true`，2 秒写稳定窗口，绕开 chokidar 的丢事件节流），
变化后走 `runExclusive()` 串行队列 → `reconcileProfilePatches()` → **普通的 Loader entry update**，
也就是 Cordis 的 epoch 驱动：fiber 重建、旧 fiber 的 `ctx.effect()` disposer **按注册逆序跑完**。

### 路径 B：源码模块热替换（默认关，`root: ["."]` 才开）

清 ESM `loadCache` + CJS `require.cache` → 重新 `import()` → 等旧 fiber 释放 →
用旧 config 在同一个 parent fiber 下重新注册。**这条路径带完整回滚**：
任一替换失败就恢复两个 module cache 并把旧 plugin 重新注册回去。

### Volatile 字段：不重挂的热更新旁路

这是 0.2.0 新增的内核机制（见 [02 Cordis 内核](02-Cordis内核机制.md)的 0.2.0 增量节）：

```ts
// vendor/cosmokit/src/volatile.ts:5-13
export type VolatileSnapshot<T> = T extends object ? { readonly [K in keyof T]: VolatileSnapshot<T[K]> } : T

/** A stable reference; keep the reference, or capture its value for one operation only. */
export interface Volatile<T> {
  get(): VolatileSnapshot<T>
}
```

**只有 volatile 变化保留实例；普通字段变化仍走既有的重挂生命周期。**

## 五、设置体系：`settings.yaml` 已删除

这条对运维影响很大。决策记录：`architecture/2026-09-19-profile-owned-live-configuration`

> *"A plugin declares every configurable value in its Cordis Config. Fields that can change
> without remounting use `.volatile()`… Settings enumerates those fields for forms and
> **never supplies business configuration**."*

```ts
// packages/settings/settings/src/index.ts:238-247
  /** Move the sections of the removed `settings.yaml` into the active profile once the Loader has settled…
   * The document is renamed before the first write, so a partial import never repeats… */
  private async importLegacyDocument(): Promise<void> {
    const profile = this.ownerContext.profileContext
    const path = join(profile.home, 'settings.yaml')
    if (!existsSync(path)) return
    const imported = `${path}.imported`
    await rename(path, imported)
```

**⚠️ 运维风险**：任何仍在往 `$DSH_HOME/settings.yaml` 写配置的自动化脚本，
在 0.2.0 上**首次启动后就会静默失效**（文件被改名），第二次写入的内容**永远不会被读取**，
只有一条 warn 日志。

**新位置**：活动 profile 的 `$DSH_HOME/profiles/<name>/cordis.patch.yml`。

### 一个必须知道的副作用

**patch 的 `config` 是整体替换，不是 merge**。所以用户一旦编辑过某个 entry，
该行会存下**写入时刻的完整 config**，**后续 bundle 对这些字段的更新就不会再传到这个 profile**，
直到用户重置整行。

## 六、可观测性（OTel）与隐私

### 分层

```
ctx.otel  (telemetry/otel)          纯传输工厂，无策略、无身份、无队列
   ├── createEventReporter()            → 普通事件通道
   └── createSessionLogReporter()       → 会话日志通道
        ↑                                   ↑
  ctx.productTelemetry               session-telemetry-otel
        ↑
  ctx.productAnalytics（仅 Desktop）
```

**只有 logs，没有 trace、没有 metric**——整个包没有 `TracerProvider` / `MeterProvider`，
端点是 `/v1/logs`。所以"OTel"在这里是**用 OTLP logs 协议当结构化事件管道**，不是分布式追踪。

### ⚠️ 默认状态与隐私面

| 通道 | 默认 | 说明 |
|---|---|---|
| `session-telemetry-otel` | **base bundle 默认挂载**，`FEEDBACK_ONLY` | 只有用户**显式提交 feedback** 才释放一段有界的会话前缀 |
| `product-telemetry-otel` | 仅 Desktop | 发什么完全由调用方决定 |
| `client/product-analytics` | **Desktop 默认 `enabled: true`，且明确写着"没有面向用户的控制"** | device_id / user_id / os_version / app_version |

Note 里的坦白值得引用（`2026-08-25-feedback-gated-telemetry-default`）：

> *"Without a deployment redaction rule, exported data **can include message text,
> tool arguments and results, and workspace paths**."*

默认端点指向 `https://dsh-otel-collector.deepseeksvc.com/v1/logs`，
身份是 `$DSH_HOME/.anonymous-user-id`（随机 UUID，删文件即重置）。

**硬退出开关**：`DSH_TELEMETRY_DISABLED` 任意非空值（**包括 `'0'` / `'false'`**）→
启动器直接把该行 patch 成 `disabled`。实现注释写得很明确：
*"a privacy switch prefers off-by-mistake over on-by-mistake"*。
软开关是 `DSH_TELEMETRY_MODE=DISABLED`。

## 七、📌 写插件的可执行清单（0.2.0 版）

1. **`package.json` 加 `engines.dsh`**——否则安装前检查和启动检查读不到范围。
2. **加 `dsh.manifestVersion: 1`**，并考虑 `icon`（≤256 KiB）+ 本地化 title/description。
   这些会显示在 Web Plugins 页，且**不需要 import 你的插件就能读出来**。
   共享类型在 `@deepseek-ai/dsh-package-manifest`。
3. **配置字段全部声明在 Cordis Config 里**；"改了不该重挂"的字段打 `.volatile()`，
   否则用户每改一次配置你的服务就被 dispose 重建一次。
4. **不要依赖"失败会回滚"**。所有资源释放必须走 `ctx.effect()` disposer——
   那是 reconcile 时**唯一保证被 await** 的路径。
5. **想让插件能被运行时安装，必须声明 `dsh.bundle`**——`installBundle` 明确拒绝非 bundle 包。
6. 本地开发迭代：把 hmr 行改成 `root: ["."]` 开启源码热替换（**唯一带回滚**的路径）。

> 另有一条容易误解的：`ctx.pluginRegistryProbe` **不是插件市场**。
> 它只是并发 ping npmjs 和 npmmirror、谁先成功用谁（1.5 秒超时 + 5 分钟缓存），
> 给安装对话框挑镜像用。**仓库里没有任何插件市场 / 插件目录服务**。
