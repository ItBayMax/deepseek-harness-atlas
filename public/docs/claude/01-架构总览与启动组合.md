# 架构总览与启动组合 —— 从一条命令到一棵插件树

> 本文是 Claude 基于源码阅读的独立解读，非官方文档。对应源码：
> `apps/cli/src/`（bin/args/profile-boot）、`packages/boot/app-boot/src/`、`packages/bundle/{base,web-app,headless}/cordis.patch.yml`、`packages/preset/agent-presets/`。

## dsh 是什么

DeepSeek Harness（`dsh`）是一个 **agent harness（智能体运行时脚手架）**：它不是某个固定形态的产品，而是一套"把 LLM agent 所需的一切——模型适配、工具、会话、沙箱、审批、UI——全部做成可插拔插件"的框架。跑 `npx @deepseek-ai/dsh web` 得到的 Web 产品，只是官方用这套插件拼出来的**一种默认组合**。

核心口号：**everything is a plugin，没有特权核心可改**。想扩展 dsh，永远是"在旁边挂一个插件"，不是"改核心代码"。

## 启动流水线（源码级）

入口 `apps/cli/src/bin.ts` → `profile-boot.ts` 的 `runProfile()`：

```text
1. loadLayeredEnv('dsh')       环境分层：继承 env > 调用目录 .env > $DSH_HOME/.env
2. composeProfile(name, patches)
   ├─ 修复 $DSH_HOME/profiles/node_modules 符号链接（BFS 依赖闭包）
   ├─ 每次启动把 profiles/<name>/cordis.yml 重写为空列表根
   └─ 补丁层按序叠加（全部是 include 的 PatchOptions）：
        bundle 补丁（按 profile 声明顺序）
        → profile 自己的 cordis.patch.yml
        → $DSH_HOME/cordis.patch.yml（家目录层，权重更高）
        → --patch 命令行覆盖（按 argv 顺序）
        → 应用注入的覆盖（shipped preset 根、遥测开关）
3. boot()                      new Context() → 挂 Loader → provide dshHomePath/cmdline
                               → mountRootInclude（一个 cordis:include 根 + 全部补丁）
                               → loader.await() → assertEntriesActivated（fail loud）
4. 若组合没启 hmr：launcher 自己挂 timer+hmr，watch 用户补丁文件实现"live 配置层"
```

**理解要点：整棵运行时插件树 = 空根 + 一摞补丁。** 每一行都有稳定 id，任何一层（包括你自己的 `--patch`）都能用 id 替换任意行的整个 config 或 disable 它。`dsh --profile web --dump-config` 打印的就是最终合成树。

### 补丁行长什么样

```yaml
# 目标行替换（config 整体替换，不合并！）
- id: webserver
  config: { host: 127.0.0.1, port: 3081 }

# 插入新行
- insert:
    - id: tool-cordis
      name: '@deepseek-ai/dsh-tool-cordis'

# !!js 表达式（等注入激活后懒求值）+ 条件禁用
- id: bash-sandbox
  name: '@deepseek-ai/dsh-bash-sandbox'
  disabled: !!js process.platform === 'win32'
```

一个容易踩的坑：**补丁替换的是整个 config**，不是深合并。所以 bundle 的设计纪律是"每个值只住一层"——base 层放所有模式共享的行，各模式差异值放各自 bundle。

## 三个官方 bundle 的分工

| Bundle | 角色 | 内容概要 |
|---|---|---|
| `dsh-base` | 所有 profile 的第一层 | 一份 `- insert:` 大列表：llm/session/agent/tools 脊柱、DeepSeek 适配器（默认 `deepseek-v4-flash`）、JSONL 持久化、沙箱+审批+权限预设、bash/fs/web/subagent/todo/skill 等全套工具、压缩、目标、计划模式…… |
| `dsh-web-app` | web profile 第二层 | 加 webserver + 浏览器客户端全家桶；同时 **disable 掉 base 的约 25 个 agent 面行**（tool-bash、tool-fs、plan-mode…），因为这些改由 per-session 的 agent preset 挂载；插入 `agent-presets`（default: standard） |
| `dsh-headless` | 一次性运行 | 36 行：persona、code-runtime、headless-runner（任务从 argv 注入） |

**web-app disable base 工具行**这个细节揭示了架构演进方向：宿主面（host plane）与 agent 面（agent plane）分离——工具/prompt/压缩这些"agent 的世界"由 preset 按会话组合，宿主只留服务器、持久化、RPC。

## Agent Preset：per-session 的插件树

`packages/preset/agent-presets`。一个 preset = 一个目录（`agent.cordis.yml` + 可选 `preset.yml` 元数据 + `skills/`）。官方出厂四件套：`standard` / `code` / `cordis` / `minimal`（`apps/cli/config/agent-presets/`）。

机制上的三个亮点：

1. **每 preset 一个常驻挂载（standing mount），不是每会话一棵树**。会话通过 scope 父子关系"加入"该挂载；`dsh-tools`/`dsh-system-prompt` 的解析顺序是 `agent → preset → global` 三层。
2. **组合审计**：挂载后检查——不允许未作用域的注册、不允许有行卡在 `waiting for <service>`、**不允许把服务发布进根领域**（必须 `isolate` 或挪去宿主组合）。这就是 preset yml 里 `cordis:group + isolate: { planMode: true }` 的由来。
3. **文件变更走"代际"**：composition 文件 mtime 变了 → 新会话用新代，已加入的会话保持旧代。

## 事件三域 —— 扩展点的选择地图

写插件的第一个决策是选对事件域：

| 域 | 载体 | 什么时候用 |
|---|---|---|
| **Session 事件**（`turn/*`、`user/message`、`tool/result`…） | 持久日志 + `session/event` 广播 | 事实必须在重载后还在 |
| **Agent 事件**（`agent/pre-step`、`agent/request`、`agent/turn-stopping`…） | 活的 Agent 句柄 | 观察/拦截进行中的工作 |
| **能力事件**（`fs/*`、`tools/*`、`llm/stream`…) | 各能力接缝 | 给接缝加策略/适配器，不必 import 循环 |

配套铁律：**模型可见 ⟺ 已落日志**（见 03 篇）；**新行为挂扩展点，改 loop 必须改架构文档**。

## 一图流：请求生命周期

```text
dsh web 启动 ──► 插件树激活（200+ 包按 inject 依赖自动排序）
浏览器输入 ──► apiproxy RPC ──► agent.followup(msg)
  ──► ReactLoopAgent: turn/start → pre-step waterfall → 组装 prompt
  ──► llm.stream（DeepSeek 适配器）→ assistant/chunk* 落日志
  ──► tool/call → tools 管线（pre → guard → execute → post）→ tool/result
  ──► turn/end ──► session/event 全程广播 ──► Web UI 渲染
持久化（JSONL/SQLite）、遥测、标题生成、投影缓存……全部只是这条事件流的订阅者
```
