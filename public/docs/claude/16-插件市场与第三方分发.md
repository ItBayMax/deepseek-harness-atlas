# 16 · 插件市场与第三方分发

> 基线：`dsh@0.2.1-rc.2`（上游 commit `687f282`）· 本篇为 0.2.1 全新

本轮对**第三方插件作者**影响最大的两件事：插件市场落地，以及 `engines.dsh` 从"写着好看"变成"独自裁决"。

## 一、插件市场：没有官方市场，只有一个格式

先把最容易误解的一点说清楚：**dsh 没有官方插件市场，也不随附任何索引源**。
用户指南原文就一句话：*"DSH ships no index source"*。

它提供的是**一个格式**和**一个读取器**。谁来生成索引、索引里列谁，完全是索引发布者的事。

### 一个市场 = 一个静态 JSON 文件

```json
{
  "format": 1,
  "title": { "en": "Team plugins", "zh": "团队插件" },
  "plugins": [
    {
      "name": "dsh-plugin-foo",
      "title": "Foo",
      "description": "Adds the foo tool",
      "icon": "icons/foo.svg",
      "author": "Jane Doe",
      "repository": { "url": "https://github.com/jane/dsh-plugin-foo" },
      "versions": [
        { "version": "1.1.0", "publishTimestamp": 1790476800,
          "source": { "type": "npm" }, "engines": { "dsh": ">=0.2.0-rc.2" } }
      ]
    }
  ]
}
```

硬约束：UTF-8、默认上限 128 MiB、必须 **2xx 直出且不允许重定向**。
托管在任意静态主机即可（GitHub/GitLab Pages、对象存储都行）。

`source` 只认两种形态，其他一律拒绝：

| type | 安装 spec |
|---|---|
| `{ "type": "npm", "registry"?: url }` | `<name>@<version>` |
| `{ "type": "git", "url", "commit"(40 位小写 hex), "path"? }` | `git+<url>.git#<commit>`，有 `path` 时追加 `&path:/<path>` |

图标可以内联 base64 `data:` URL，也可以是相对 URL——**相对图标按索引 URL 解析**，
和网页里 `<img>` 的规则一样。所以把 `index.json` 和 `icons/` 并排发布，换到任何主机都不用改文件。

### 读取器是"全有或全无"，但对未知成员宽容

任一规则违例（引用未声明的分类/标签/排序键、`dist-tags` 指向未列出的版本、
`name` 或 `version` 重复、`format != 1`）→ **拒绝整个索引**，并在"管理索引源"里显示
出错值的 JSON 路径。

但**每一层都忽略未知成员**——这是为 format 1 留的增量加字段空间。

> **这个组合值得抄**：对**已声明**的东西零容忍（引用不存在的分类直接废掉整份索引），
> 对**没声明**的东西完全宽容（未知字段静默忽略）。
> 前者防的是"索引看起来能用其实半坏"，后者换的是向前兼容。

### ⚠️ 没有审核，没有签名

索引**未签名**。标题、作者、标签、"官方"徽章、评分——**全都只是市场的声明**，dsh 一个都不验。

更要紧的是：Git 来源的仓库可以声明**任意包名，包括 `@deepseek-ai/dsh-` 前缀**；
npm 来源的 `source.registry` 同样可以把任意包名指向市场选定的 registry。

**dsh 只校验文件格式，不校验这些声明。** 唯一的防线是 UI：客户端必须显示索引 URL
和每个版本的 `source`，安装前弹确认框。

对应的产品态度很克制——上游把"市场是第三方内容"直接写进了用户指南：
*"Add only sources you trust, and check the source in the confirmation before installing."*

### 怎么让自己的插件被收录

只有两条路：

1. **自建市场**。仓库自带参考生成器 `apps/plugin-market-generator`：喂给它一个纯文本列表
   （每行一个 npm 包名或 https Git 仓库 URL），产出 `index.json`，自己托管。
   生成器**只下载和读取文件，从不安装包或执行其代码**。
2. **求某个第三方市场的生成器收录你的包。**

### `ctx.pluginMarket` 与它的一个关键设计

服务只读调用 `pluginManager`，**从不写 profile**。配置里有一处很值得注意：

```ts
// packages/boot/plugin-market/src/index.ts:78-83
  static Config = z.object({
    indexes: z.array(z.string().pattern(/^https?:\/\/\S+$/u)).default([]).volatile(),
    fetchTimeoutMs: z.natural().min(1).max(MAX_TIMER_DELAY_MS).default(15000),
    maxBytes: z.natural().min(1).default(128 * 1024 * 1024),
    cacheTtlMs: z.natural().default(600000),
  })
```

`indexes` 是 **`.volatile()`** 字段——这正是 0.2.0 那轮新增的 `Volatile<T>` 机制在真实场景里的用途：
Settings 只写 volatile 字段，Loader 把纯 volatile 变更提交到运行中的引用，**不重新挂载任何插件**。

为什么非这样不可：市场服务必须独立于 `plugin-manager`，而 `plugin-manager` 拥有 profile 的包操作——
**安装过程中绝不能被重新挂载**。加一个索引源如果会触发重挂，就可能把正在进行的安装打断。

另外两条约束：`search`/`entry` **只接受已配置的 URL**（否则抛 `plugin-market/unknown-index`），
Host 永不获取客户端提供的地址；只读工具 `plugin_market` **不需要批准**（列出不改任何东西），
但它**不能修改索引源**——因为加索引源等于引入新的代码来源。

## 二、`engines.dsh`：从被忽略到独自裁决

### 变化本身

v0.2.1-alpha.3 及以前：安装与 profile 启动**只看** `peerDependencies` 里的
`@deepseek-ai/dsh` / `@deepseek-ai/dsh-*`，**完全忽略 `engines.dsh`**。

下一版起反转——**自带的 `engines.dsh` 独自决定，peers 被忽略**；
只有 `engines.dsh` 缺席时才回退到 peer 规则。

```ts
// packages/boot/app-boot/src/plugin-compatibility.ts:51-61
function satisfies(runtimeVersion: string, range: string): boolean {
  return range.trim() !== '' && semver.satisfies(runtimeVersion, range, { includePrerelease: true })
}

function unmetRequirements(fields: Record<string, unknown>, runtimeVersion: string): Record<string, string> {
  const engines = Object.hasOwn(fields, 'engines') ? objectOf(fields.engines, 'Plugin manifest engines') : {}
  if (Object.hasOwn(engines, 'dsh')) {
    const range = engines.dsh
    if (typeof range !== 'string') throw new Error('Plugin manifest engines.dsh must be a string')
    return satisfies(runtimeVersion, range) ? {} : { 'engines.dsh': range }
  }
```

同时 `IncompatiblePlugin` 和 `PluginCompatibility` 把 `peers` 字段**重命名为 `requirements`**。

### `includePrerelease: true` 是个必须理解的细节

这一行关掉了 semver 默认的"先行版只能匹配同元组且带先行版的比较器"规则。
后果是**非对称**的，很容易踩：

| runtime | `^0.2.0` 能装吗 |
|---|---|
| `0.2.1-rc.2` | ✅ 能（默认 semver 下 ❌） |
| `0.2.1` | ✅ |
| `0.2.0-rc.2` | ❌ **不能** |
| `0.3.0` | ❌ |

注意第三行。**`^0.2.0` 拒绝 `0.2.0-rc.2`**，因为 `0.2.0-rc.2 < 0.2.0`，
`includePrerelease` 放宽的是上界侧的比较器，不是下界。

我们自己的 `dsh-replay-theater` 正好踩了这个：它写 `engines.dsh: "^0.2.0"`，
而 README 里声明的开发基线是 `0.2.0-rc.2`——**那个范围会拒掉它自己的基线版本**。
已改成 `^0.2.0-rc.2`。

> **可抄的规则**：若你的插件支持从某个 rc 开始，范围的下界就要**写到那个 rc**，
> 而不是写它对应的正式版。

### 失败模式是 fail-closed

- 安装时：plugin-manager 返回 `incompatible-version` 拒绝记录
- 启动时：不兼容的行被**从组合中剔除**（deny），stderr 打印警告
- `engines` 不是对象、`engines.dsh` 不是字符串 → **抛错**，manifest 视为不可读 → **整包被拒**
- `workspace:` 前缀**只在 peers 里合法**，写进 `engines.dsh` 恒为不满足
- 唯一放行方式：`dsh plugin allow-version`，粒度是 `name@version` → 具体 runtime 版本

### ⚠️ 别忘了 `dsh.bundle`

这一条与 `engines` 无关但同样会卡住安装：

```ts
// packages/boot/plugin-manager/src/index.ts:440
if (!inspection.bundle) return refused('not-a-bundle', `${inspection.name} declares no dsh.bundle`)
```

判定依据是 `manifest.dsh?.bundle?.patch === undefined`。CLI 路径不拒绝，但会降级：

```
dsh: warning: <name> declares no dsh.bundle — installed as a plain dependency, not a profile layer
```

**降级是静默的失败模式**——包装上了，但不作为 profile layer 生效。

## 三、三处上游自身的文档漂移

本轮核对时发现的，记在这里以免下次被带偏：

1. **`packages/util/package-manifest/README.md:93`（中英双份）已半数失效**，原文：
   > Compatibility is declarative. Current installers and loaders do not enforce
   > `dsh.manifestVersion` or `engines.dsh`; declaring a range does not reject
   > incompatible hosts or validate SemVer syntax.

   `engines.dsh` 部分**完全反了**：现在强制检查、会拒绝不兼容宿主、也会校验
   （非字符串直接抛错）。`manifestVersion` 部分仍然成立——全仓只有一处类型声明
   （`packages/util/package-manifest/src/types.ts:32`），没有任何校验点。

2. **索引里 `engines` 到底必填？Note 与实现冲突。**
   `.agents/notes/.../2026-10-02-plugin-market-index-format.zh.md` 的字段表写"必填"，
   但实现是可选（`packages/util/plugin-market-index/src/types.ts:62-63`：
   *"absent means any DSH version"*），用户指南也写 `no`。
   **以代码为准：可省，省了等于 `*`。**

3. **`2026-10-06-web-desktop-plugin-identity-compatibility` 标题误导。**
   它不是在讲"web 与 desktop 的插件身份不兼容"——没有这个问题。
   它讲的是把能力迁进 `packages/experimental/` 时如何不破坏既有 profile 配置：
   迁移的包**保留已发布的包名**，不加 experimental 前缀。

## 四、关于"插件预览图"——第三方目前完全无份

容易误读的一条。`built-in plugin feature previews` 里的 "built-in" **特指随 dsh 发布的官方组合包**。

cookbook 原文（`docs/cookbook/adding-a-plugin-preview.md:5`）：

> Packages cannot declare illustrations through their manifest or exports;
> **third-party plugins have no preview interface.**

机制是硬编码在 `packages/client/ui-plugin-manager/src/client/PluginManagerPage.tsx:163`
的 `BUNDLE_PREVIEWS` 映射（包名 → `{ en, zh }` 两份 SVG），以 data URL 内嵌进 bundle。

被明确否决的替代方案：在 manifest 里加 `preview` 字段——理由是
"只有一个官方组合包有配图，不足以支持一个公开格式"。

长期计划是让第三方插件在插件管理里展示自己的 README，届时会定义独立的格式与信任规则。
**目前没有可用路径。**

## 五、免重启升级：实际是怎么做到的

`plugin-install-over-installed` + `profile-package-refresh` + `replace-changed-package-modules`
三条合起来才是完整链路。核心难点很具体：

**pnpm hoisted 布局让包永远在 `node_modules/<name>`，覆盖/升级/重装后所有文件 URL 不变**，
而 Node 按 URL 缓存模块——于是导入拿到的还是旧模块。

解法是 `Hmr.reconcileProfile()` 成为唯一重新组合入口，六步串行：
读 patch 并把已加载模块与磁盘比对 → 规划替换（失败则在**任何模块变化之前**抛错）→
逐出陈旧模块及其导入方 → 删除运行时以停止被替换插件的 Loader entry →
**一次** `recomposeProfile()` → 逐出被删映射目录下的模块。

变化检测记录 **inode、大小、修改时间**，**刻意不记状态变更时间**——
因为 pnpm 硬链接导入会改 ctime 而内容不变。也**不比版本号**，因为 lockfile
不为 `file:`/`link:` 记内容标识。

配套的入口收窄：在跑 HMR 的 profile 下（出厂 profile 都跑 HMR），对已安装包
`installBundle(spec)` 在 **pnpm 运行之前就失败**（`already-installed`），**不改动任何 profile 文件**。
正确路径是 **`removeBundle(name)` 然后 `installBundle(spec)`**。

已知缺口，对第三方作者有实际影响：
- **只改 `package.json` 的变化检测不到**
- **在 Plugin Manager 之外执行的安装**要等下一次重新组合或重启
- 打包 worker loader 的模块存在私有映射里，HMR 换不掉，一律报需要重启

换不掉的归入 `pending` 并带**结构化** `restartReason`（枚举 `host-module` /
`unmanaged-plugin` / `module-comparison`），**没有任何界面解析诊断字符串**——
这一条是很好的接口设计样本。

## 六、顺带：`dsh plugin` 的命令行写法变了

不是清单变化，是 CLI 选项解析：`dsh plugin` 现在**只在转发给 pnpm 的参数之前**读 `--profile`。

```bash
# ❌ 现在会报 required option '--profile <name>' not specified
dsh plugin add <pkg> --profile <name>

# ✅
dsh plugin --profile <name> add <pkg>
```

对包清单无影响，但**会打断既有的安装脚本和 CI**。
